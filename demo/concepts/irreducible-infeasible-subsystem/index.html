Concept 01 / Model diagnosis

Find the contradiction, not just the failure.

An irreducible infeasible subsystem turns “no solution exists” into a focused set of constraints and bounds that cannot all hold. It is evidence for debugging, not an instruction to delete a requirement.

01

Feasibility comes before optimality

A model is feasible if at least one assignment of all decision variables satisfies every row constraint and every variable bound, within the solver's feasibility tolerances. The objective chooses among feasible assignments; it cannot make an impossible constraint set feasible.

An infeasible status is a proof that no such assignment exists. Before requesting an IIS, distinguish that proof from statuses such as unbounded-or-infeasible, interrupted, or a time limit. Those outcomes do not establish the premise that an IIS analysis needs.

Practical distinction: an unbounded model has feasible points but no finite optimum in the objective direction. An infeasible model has no feasible point at all.
02

A small certificate of conflict

Formal definition

Given a finite set of row constraints and variable bounds, an IIS is a subset that is infeasible and becomes feasible when any single member of that subset is removed.

The definition is local to the returned subset. Constraints outside it may still participate in another contradiction, and solving one IIS does not prove the entire repaired model feasible.

Irreducible

No member is redundant within this conflict. Remove any one member and this subsystem becomes feasible.

Minimum-cardinality

No IIS anywhere in the model contains fewer members. An IIS routine does not generally promise this stronger property.

Independent data errors can create disjoint IISs; overlapping constraints can create many alternatives. The IIS returned on one run is therefore one explanation, not necessarily the only explanation or the one a domain expert will find easiest to repair.

03

Rows and variable bounds are both requirements

A row applies a linear expression bound such as 5 ≤ 2x + y ≤ 9. A column bound applies directly to one variable, such as 0 ≤ x ≤ 4. Either side can be the member that creates a conflict.

StatusMeaning in the retained itemExample
boundLowerThe lower side participates.x ≥ 4 or 2x + y ≥ 5
boundUpperThe upper side participates.x ≤ 4 or 2x + y ≤ 9
boundBoxedBoth finite sides are retained.1 ≤ x ≤ 4
boundFreeNo finite active bound is identified; do not interpret it as a lower or upper bound.An otherwise free retained item

“Column” does not mean “objective coefficient.” The objective is irrelevant to feasibility. A column entry identifies a model variable and the bound classification associated with it.

04

Read getIis() as aligned arrays

Model.getIis() returns detached typed arrays. Compact arrays describe retained items; status arrays describe every row or column in model order.

colIndex
Zero-based model column indices retained in the compact result.
colBound
Parallel to colIndex. Entry colBound[i] classifies the bound for model column colIndex[i].
rowIndex
Zero-based model row indices retained in the compact result.
rowBound
Parallel to rowIndex. Entry rowBound[i] classifies the bound for model row rowIndex[i].
colStatus
One entry per model column: compare with notInConflict, maybeInConflict, or inConflict.
rowStatus
One entry per model row, using the same membership constants.

Compare numeric codes with highs.constants.iis, not hard-coded numbers. Resolve indices against the same loaded model using names and snapshots such as getColName(), getRowName(), getCols(), and getRows(). Preserve that context before calling dispose().

Do not zip rows with columns. The row and column compact arrays are separate axes and can have different lengths. Only each index array and its corresponding bound array are parallel.

An empty compact result means no subsystem was found; it does not by itself prove feasibility. A limited computation may also leave maybeInConflict statuses and may not have established irreducibility.

05

A debugging workflow that preserves intent

  1. Confirm the status. Solve first and proceed only after the model status proves infeasibility.
  2. Freeze the evidence. Record the model version, input data, row and column names, units, bounds, and solver tolerances used for the failing run.
  3. Compute and map the IIS. Translate every returned index and bound code back to a human-readable model requirement. Inspect both row bounds and variable bounds.
  4. Check formulation before policy. Look for sign reversals, unit mismatches, stale joins, swapped lower and upper bounds, accidental defaults, rounding, and duplicated requirements.
  5. Ask which requirement may move. A domain owner should decide whether a member is wrong or relaxable. The solver identifies conflict, not business priority.
  6. Change one assumption and solve again. Verify the intended repair on the full model. If it remains infeasible, compute another IIS and continue.

To search for alternative IISs, temporarily relax or exclude one member of the current IIS and rerun conflict analysis. This is an exploration technique, not permission to remove that member from production.

06

What an IIS cannot tell you

  • It does not select the correct business requirement to relax.
  • It does not guarantee the fewest-member conflict or enumerate every IIS.
  • It does not quantify the smallest useful relaxation; use a feasibility relaxation or a purpose-built repair model for that question.
  • It does not make poor scaling harmless. Near-conflicts can change classification when data scale and feasibility tolerances change.
  • It does not replace validation of generated model names, indices, units, and source records.

For a foundational treatment, see John W. Chinneck and Erik W. Dravnieks, “Locating Minimal Infeasible Constraint Sets in Linear Programs”, ORSA Journal on Computing (1991).
